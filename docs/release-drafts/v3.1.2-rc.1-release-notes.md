# darklab_shell 3.1.2-rc.1 release notes

This release candidate fixes workspace access and cleanup issues in the 3.1 series. It includes the pseudonymous principal, restricted-access, OIDC, and API authentication model introduced in earlier v3 releases. Those compatibility requirements still apply when upgrading from an older installation.

## Fixes in this candidate

- Workspace requests without an identity return HTTP 401 instead of a server error. If a browser loses its session cookie, signing in again restores its saved preferences, stars, and active Project. Public run permalinks retain their existing visibility rules.
- Expired, revoked, or otherwise rejected browser sessions no longer produce workspace cleanup errors or postpone the next eligible cleanup attempt. Genuine maintenance failures still produce error logs.
- Cleanup protects the current workspace after an anonymous workspace has been kept, including when it retains its original directory.
- Browser and terminal regression tests handle delayed test-hook loading and deferred stream exits without leaking state into later tests.

## Workspace identity and compatibility

Pseudonymous principals give kept workspaces a stable identity. You don't need an email address or a conventional account profile. Portable browser credentials can be labeled, rotated, and revoked without changing the workspace. Browsers exchange them for protected sessions; API integrations use separate scoped personal access tokens (PATs).

**Legacy `tok_` values are intentionally invalid.** They cannot sign in or authorize API requests, and renaming an old value doesn't convert it into a supported credential. SQLite and Postgres databases containing retired identity tables or ownership columns are rejected at startup. The old conversion helper isn't included. Test a restored copy first; an incompatible installation needs a separate data transition or a fresh installation.

## Private deployments and OIDC

Choose the access policy that fits the installation:

| Profile | Browser access |
| --- | --- |
| `open` | Anonymous workspaces remain available. Users can keep a workspace for later access. |
| `token_required` | A portable credential is required to sign in. |
| `oidc_required` | Sign-in uses the configured OpenID Connect provider. |
| `mixed` | Either a portable credential or the configured provider can sign in. |

OIDC uses the authorization-code flow with PKCE. The app keeps the provider issuer and subject as the identity link; it doesn't require an email address, name, or provider groups. Provisioning can be disabled, restricted to allowed subjects, or automatic. Provider groups don't grant Team roles or operator access.

Authenticated browser access requires HTTPS outside browser-supported localhost exceptions. OIDC requires an HTTPS issuer and callback. Follow [restricted browser access](../../CONFIGURATION.md#restricted-browser-access) for bootstrap, provider settings, and local recovery.

## API and CLI authentication

API v1 and the `darklab` CLI require scoped PATs. Portable browser credentials can't authenticate API v1 requests. Create a PAT in **Options → Access → Add credential → API token (PAT)**, select the permissions each integration needs, and save the one-time value securely.

Use the CLI's `--pat` option, `DARKLAB_PAT` environment variable, or `pat` configuration setting. Reissue credentials for older integrations and update them before upgrading. PAT rotation preserves its expiry, so check both permissions and remaining lifetime. See [API authentication](../api.md#auth) and [CLI configuration](../../CONFIGURATION.md#headless-cli-configuration).

## Required operator preflight

Complete the [upgrade preflight](../../CONFIGURATION.md#upgrade-preflight) before changing the live image or database:

1. Check schema compatibility on a disposable restored copy. Run the candidate's strict configuration checker against the intended settings.
2. Verify a working credential or provider sign-in and the local recovery path. Operator pages require an explicit principal grant and recent verification; bootstrap credentials and Team roles don't grant console access. OIDC operator verification also requires a signed authentication-time claim.
3. Update API and CLI integrations to scoped PATs. When upgrading from before 3.1, rename `diagnostics_allowed_cidrs` to `metrics_allowed_cidrs` and update audit bookmarks to `/audit`.
4. Stop writes and take a complete backup of the database, matching secrets key, Files, `.env`, `conf/`, operator Compose settings, and release metadata. Verify checksums and rehearse restoring to a separate target with the original release. Keep a separate copy of `compose.operator.yaml` if an older backup helper omits it.
5. Verify the exact candidate's signed checksum manifest and image digest. After the upgrade, check health, browser sign-in, saved workspace state, API access, operator verification, and metrics scraping.

Keep the pre-upgrade backup until those checks pass. Schema changes can be forward-only: rollback means restoring the matching pre-upgrade state, not merely choosing an older image. See [Operator Backups](../../CONFIGURATION.md#operator-backups).

# darklab_shell 3.1.1-rc.1 release notes

darklab_shell 3.1.1-rc.1 improves mobile sign-in and Status Monitor interactions, fixes a sign-in race, and updates JavaScript dependencies to address reported security advisories. It's a release candidate for the 3.1 series.

The access and upgrade guidance below also covers the changes introduced in 3.0 and 3.1.0, so operators coming from an older installation can review the requirements in one place. Those capabilities are already part of v3; they aren't new features in this patch.

## Changes in this candidate

### Sign-in stays on the restored workspace

A late authentication error from an anonymous request or a previous browser session no longer interrupts a successful sign-in. This also covers access changes made in another tab.

On mobile, tapping the credential field no longer zooms the page. The same behavior applies when verifying access to operator pages.

### Mobile Status Monitor is easier to use

Constellation and Command Territory legends wrap above their charts, keeping labels readable on narrow screens. Tap a star or territory to preview it, then choose **Open run** or **View history** in the pop-up. Swiping scrolls the chart without opening a run or History. Desktop interactions stay the same.

### Updated dependencies and reliable checks

The JavaScript dependency tree includes patched releases for the reported npm advisories. Mobile scrolling checks work on Linux CI runners as well as macOS, and credential-expiry checks stay valid as the calendar advances.

## Access and authentication in v3

### A workspace belongs to a pseudonymous principal

The v3 principal model separates your saved workspace from the credentials you use to reach it. You don't need a username, email address, or password. Rotating a credential or changing sign-in methods preserves your personal workspace and Team membership.

- In an open deployment, **Options → Access → Keep this workspace** keeps an anonymous workspace and gives you a portable credential to save.
- Use **Options → Access** to manage device credentials, API tokens, linked provider sign-in, and browser sessions.
- Save each new credential when it's shown. The app can't reveal it again later.

See [Workspace Access](../../FEATURES.md#workspace-access) for everyday use and [principal access operations](../../CONFIGURATION.md#principal-access-operations) for operator recovery.

### Legacy `tok_` values are intentionally invalid

The old session-token model is retired. A legacy `tok_` value can't sign in or authorize an API request, and changing its prefix doesn't make it a valid credential.

The application also rejects databases with retired identity tables or ownership columns. The old conversion helper isn't included. Check compatibility using a disposable restored copy before upgrading; an incompatible database needs a separate data transition or a fresh installation. Don't treat an image change as an automatic identity migration.

### Restricted deployments require sign-in

The default `open` profile supports anonymous workspaces on trusted networks. Private deployments can choose `token_required`, `oidc_required`, or `mixed` to require a portable credential, provider sign-in, or either method. Restricted profiles disable anonymous access and public credential issuance. Public sharing is disabled by default in those profiles.

Authenticated browser access requires HTTPS in every profile. The browser uses a temporary protected session after sign-in, and **Log out** ends that session without deleting the workspace. A fresh credential-required installation uses the local deployment helper to create its first principal and save the credential to a private file.

Follow [restricted browser access](../../CONFIGURATION.md#restricted-browser-access) for profile selection, bootstrap, HTTPS, and session settings.

### OpenID Connect support

OIDC lets people sign in through an operator-configured identity provider. The app links the provider's issuer and subject to a principal without requiring a real name or email address. Operators control whether new provider identities can create workspaces.

Link an existing workspace before changing its deployment to provider-only sign-in. Linking needs recent proof of both identities, and unlinking needs a usable recovery credential. Provider-only deployments still support scoped PATs for API clients.

Check [provider compatibility](../../CONFIGURATION.md#provider-compatibility), including the exact callback, client authentication, signed token requirements, and fresh provider proof needed for operator verification.

### API and CLI authentication use scoped PATs

API v1 accepts personal access tokens through `Authorization: Bearer`. Portable browser credentials and anonymous identities don't authenticate API requests. PATs have an expiry and selected permissions, and can't access browser product routes or create more credentials.

Update integrations to use `--pat`, `DARKLAB_PAT`, or the CLI's `pat` configuration key. The old `--token`, `DARKLAB_TOKEN`, and `token` settings are removed. Create a separate PAT for each integration, store it privately, and verify the intended identity and permissions with `darklab whoami`.

See [Create a PAT](../api.md#create-a-pat) and [CLI configuration](../api.md#cli-configuration) for issuance, private transfer, expiry, rotation, and verification.

## Operator changes in the 3.1 series

Diagnostics, Audit log, and Operator settings require an explicit principal grant and a recently verified browser session in every access profile, including `open`. Team roles, portable credentials, and PATs alone don't grant console access. The local `darklab-deploy access` commands support grant management and recovery.

- Update audit bookmarks from `/diag/audit` and `/diag/audit/export` to `/audit` and `/audit/export`; the old routes don't redirect.
- Rename `diagnostics_allowed_cidrs` to `metrics_allowed_cidrs` in every configuration layer. The removed key is ignored and doesn't enable metrics scraping.
- Keep metrics network permissions separate from operator grants. An operator grant doesn't authorize a Prometheus scrape.

Follow [operator setup](../../CONFIGURATION.md#operator-settings-console) and [metrics configuration](../../CONFIGURATION.md#enable-diagnostics) before changing the image.

## Required upgrade preflight and backup

Complete the [operator upgrade preflight](../../CONFIGURATION.md#upgrade-preflight) before changing the image or database:

1. **Check database compatibility on a disposable restored copy.** Confirm principal-owned data and a usable credential or provider sign-in. Retired `tok_` credentials and identity schemas aren't supported.
2. **Keep a working recovery path.** Verify HTTPS, trusted proxy settings, the chosen access profile, provider configuration where applicable, and the local access commands. Confirm the operator's explicit grant and recent browser verification.
3. **Update integrations and configuration.** Replace legacy CLI authentication settings, issue scoped PATs, rename the removed metrics setting, and update audit URLs. Run the candidate's configuration checker with `--strict`; this checks configuration, not database compatibility or provider availability.
4. **Stop writes and verify a complete backup.** Preserve the database, matching secrets key, Files, `.env`, `conf/`, `compose.operator.yaml`, and release metadata together. Check archive checksums and rehearse recovery on a separate target using the original release. Keep a separate copy of `compose.operator.yaml` if the older backup helper doesn't include it.
5. **Verify the exact candidate artifacts before startup.** Use version `3.1.1-rc.1` and tag `v3.1.1-rc.1` when checking the signed checksum manifest and image digest. Compare release-owned files with your installation's settings before recreating the app.
6. **Check the upgraded installation.** Verify health, browser sign-in, API access, operator verification, and metrics scraping. Keep the pre-upgrade backup until these checks are complete.

Schema changes can be forward-only. Rollback means restoring the matching pre-upgrade database, secrets key, files, and configuration; selecting an older image alone doesn't reverse a migration. See [Operator Backups](../../CONFIGURATION.md#operator-backups) for the supported backup and recovery procedures.

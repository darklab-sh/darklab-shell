## [2.8.4] - Unreleased

### Added

- **Projects now have a durable assessment-cycle and evidence foundation.**
  - **Why:** Assessment coverage needs to remain explainable after a cycle finishes or a source run is cleaned up, without copying source records into a second history system.
  - **What:** Shared SQLite/Postgres tables store versioned cycle snapshots, target-specific checks, and typed evidence references. Database constraints allow one active cycle per Project, reject unsupported states and evidence kinds, prevent duplicate checks and evidence links, and require complete unavailable-source tombstones. Project deletion removes the assessment tree explicitly on both backends, while owner, Project, status, check, target, and evidence indexes keep later list and rollup queries bounded.
  - **Tests:** Migration, schema-manifest, SQLite/Postgres parity, index, lifecycle, duplicate, invalid-state, tombstone, and Project-cleanup coverage pins the shared contract.
- **Assessment cycles now have a strict, versioned profile catalog.**
  - **Why:** Coverage needs a stable definition of what was checked, which saved evidence counts, and what action should come next before cycles can be created or scored.
  - **What:** Maintained Network and Web profiles define versioned checks, target types, policy levels, explicit evidence match rules, validated command/workflow recommendations, and plain-language completion guidance. Operators can add a complete profile or replace one complete profile by key through `assessment_profiles.local.yaml`; checks never merge piecemeal, and a rejected hot reload keeps the last valid catalog active.
  - **Tests:** Focused catalog coverage pins shipped definitions, atomic local add/replace behavior, hot reload and recovery, last-good fallback, shared config-root resolution, strict keys/types/policies/action references, size limits, and release-installer starter files.
- **Projects can now create and read owner-scoped assessment-cycle snapshots through one shared service contract.**
  - **Why:** Browser, API, package, and report surfaces need one trustworthy source for what a cycle contains and how its coverage is counted before they expose assessment actions.
  - **What:** Cycle creation validates the Project's personal or team scope, rejects archived Projects and duplicate active cycles, snapshots the selected profile, and expands its checks only across confirmed compatible targets. Configurable owner and Project quotas bound saved cycles and target-specific checks in the insert transaction. The shared read model provides deterministic paging and filters plus cycle and category rollups for applicable, covered, awaiting-review, untested, excluded, and unavailable-evidence checks without exposing personal session ids or mutating evidence on read.
  - **Tests:** Focused service coverage pins immutable snapshots, confirmed-target selection, unsupported profiles, archived and out-of-scope Projects, active-cycle conflicts, personal/team isolation, transactional quota rollback, safe serialization, bounded paging and filters, and truthful rollup denominators.
- **Assessment checks now have an explicit saved-evidence matcher and incremental state derivation contract.**
  - **Why:** Linking a run to a Project doesn't prove that it tested the right target with the right tool or completed successfully.
  - **What:** The assessment domain builds bounded facts from typed command targets, scan observations, workflow provenance, Atlas entities, findings, and artifacts, then applies the cycle's immutable evidence rules. Compatible links are idempotent and quota-bound in one transaction; clean negative evidence stays factual, finding-bearing rules move to review, and derived evidence never overwrites a deliberate manual exclusion. Completed runs linked manually, through the active Project, or by auto-promote reconcile only after their findings, entities, targets, and scan observations are saved; unlinked runs skip the work. A matching or quota failure rolls back that optional assessment work without losing the run. Deleting one run, a selected group, filtered History records, or automatically expired records keeps each assessment reference as an unavailable-source tombstone, including its original observation time, instead of silently erasing historical coverage.
  - **Tests:** Focused SQLite and PostgreSQL coverage pins exact and descendant target boundaries, command/completion/version/structured-output requirements, unrelated linked-run rejection, idempotency, manual-state protection, finding-aware derivation, all-or-nothing evidence quotas, completed-run integration and failure isolation, and tombstones across every History and retention deletion path.
- **Assessment cycles now have a forward-only lifecycle and safe cleanup routes.**
  - **Why:** An assessment needs to remain trustworthy after completion, while operators still need a deliberate way to hide or remove old cycles without deleting their original evidence.
  - **What:** Project routes can list, create, read, rename, complete, archive, preview deletion, and delete assessment cycles within the existing personal or team scope. Active cycles may be completed or archived, completed cycles may only be archived, and neither can be reopened or edited. Hard deletion is limited to archived cycles, reports exactly how many checks and evidence links will be removed, and preserves every referenced run, finding, entity, and artifact. Lifecycle mutations use the existing Project capability, rate-limit, safe-log, and audit boundaries; deletion and its audit record commit together.
  - **Tests:** Focused SQLite, PostgreSQL, route, audit, architecture-inventory, scope, paging, transition, preview, and source-preservation coverage pins the lifecycle contract.
- **Assessment checks now support reasoned manual decisions and validated saved evidence.**
  - **Why:** Assessors need to explain deliberate exclusions and attach supporting records without letting an unrelated or out-of-scope source claim coverage.
  - **What:** Active-cycle checks can be marked blocked, skipped, or not applicable with a required reason and safe actor metadata, then returned to their evidence-derived state. Runs, findings, Atlas entities, workflow executions, output artifacts, and workspace artifacts are accepted only when they belong to the Project and satisfy the cycle's frozen evidence rule. Manual links can be removed, while reconciled evidence stays tied to its source lifecycle. Session-token migration carries personal assessment ownership and actor references forward. Every mutation is rate-limited, logged without source contents, and committed with a fail-closed audit event; completed and archived cycles remain immutable.
  - **Tests:** Focused SQLite and PostgreSQL coverage pins reasons, actor metadata, clearing and state re-derivation, compatible and cross-scope evidence validation, manual exclusion preservation, link removal, session migration, immutable completed cycles, audit events, and transactional rollback when audit recording fails.
- **Assessment cycles are now available through the token-authenticated API and bundled CLI.**
  - **Why:** Scripts and integrations need the same truthful cycle, check, and evidence contract as the browser without bypassing Project scope or team permissions.
  - **What:** API v1 can list, create, read, rename, complete, archive, preview deletion, and delete assessment cycles; filter their bounded check pages; save or clear reasoned manual states; and link or unlink validated evidence. `darklab assessment` can list and inspect those cycles, page and filter checks, record a reasoned exclusion, or restore a check to its evidence-derived state. Personal and team requests reuse the assessment services, safe serializers, audit trail, rate limits, and `MUTATE_PROJECTS` capability checks. The OpenAPI contract documents every request, response, filter, lifecycle conflict, and privacy boundary without exposing session ids, profile paths, secrets, or stored command context.
  - **Tests:** API lifecycle, personal/team isolation, viewer permissions, error-envelope, audit, privacy, OpenAPI snapshot, CLI request/output/completion, route-inventory, and module-ratchet coverage pins the public contract.
- **Projects now include an Assessment tab on desktop and mobile.**
  - **Why:** Assessors need to see what has actually been tested, what still needs attention, and which saved evidence supports that answer without leaving the Project workspace.
  - **What:** The shared Project tabs can start a profile-driven assessment cycle, switch between saved cycles, show coverage and category progress, filter and page target-specific checks, and expand each target's saved work. Covered, awaiting-review, untested, excluded, manual-decision, and unavailable-evidence states stay distinct in text and badges. Operators can complete or archive a cycle with a warning confirmation, then preview and permanently delete an archived cycle without deleting its source runs, findings, entities, or files. Desktop uses normal action buttons, mobile uses the shared action sheet and sticky footer, and view-only members see disabled controls. The tab keeps its cycle, filters, page, expanded targets, and reading position per Project and loads its controller and styles only when opened.
  - **Tests:** Browser-route coverage pins the safe profile catalog, while focused browser tests pin lazy loading, desktop/mobile parity, disclosure behavior, filters, paging, state restoration, profile-driven creation, forward-only lifecycle confirmations, deletion-preview copy, cancellation, and view-only permissions.
- **Findings now include offline EPSS and CISA KEV context, with feed-driven Project Monitoring alerts.**
  - **Why:** Assessors can put known-exploited and higher-probability CVEs first without sending saved targets or findings to another provider when they open a result.
  - **What:**
    - Release-pinned, attributed FIRST EPSS and CISA KEV snapshots provide a dated offline baseline. Operators can opt into daily allowlisted refreshes with conditional requests, database leases, strict validation, bounded retries, and last-good fallback; `providers` shows the current source and freshness state.
    - `intel cve`, Atlas, Project Findings, reports, evidence packages, API responses, and desktop/mobile finding rows use the same stored public-risk signals. KEV, EPSS, and NVD CVSS stay separate; missing, stale, disputed, rejected, and withdrawn data remains explicit; and CISA dates are labeled as federal context rather than an operator SLA.
    - Operators can load bounded NVD 2.0 JSON from a local file or allow an explicit, capability-checked Atlas CVE Intel refresh to retain the normalized advisory status, CVSS vector/score, and CWE ids. Both modes preserve source versions, positive and negative cache expiry, attribution, and last-good data without sending saved product inventories automatically.
    - Findings are ordered by KEV, EPSS probability and percentile, stored CVSS, then age. Reports and evidence packages pin the exact source versions and values used so an older export stays explainable.
    - Multiple observations of the same CVE on the same exact affected subject share one owner-scoped remediation identity. The shared fix-first worklist contract counts that identity once, reports its observation and evidence totals, and keeps validation method, confidence, exposure, and asset context visible without letting those contextual fields silently change the public-risk order.
    - Accepted feed changes can raise owner-scoped KEV and EPSS threshold events without rescanning. Durable work cursors, EPSS hysteresis, canonical acknowledgements, Project projections, and an opt-in digest setting prevent replay, flapping, duplicate Project alerts, and cross-owner disclosure.
    - Later NVD records preserve disputes, rejection, withdrawal, reinstatement, and material CVSS downgrades as source-versioned Project Monitoring history. A first accepted record stays silent, while the default 1.0-point downgrade threshold can be tuned without rewriting saved findings or earlier occurrences.
  - **Tests:** Focused backend coverage exercises bundle and NVD dataset validation, refresh safety, positive/negative advisory caching, last-good fallback, stale and unavailable states, ranking, exact remediation grouping, evidence counts, owner and subject boundaries, queue fairness and retries, escalation hysteresis, NVD transition deduplication and source-version preservation, acknowledgement scope, report provenance, configuration bounds, and privacy-safe errors. Browser unit coverage pins compact KEV/EPSS/CVSS labels plus Project Monitoring acknowledgement, digest behavior, and NVD change labels; route, SQLite/Postgres migration, architecture, OpenAPI, asset, and documentation checks cover the shared schema and public contracts.
- **Atlas now has an exact, read-only lookup workflow for saved hostnames, IP addresses, and HTTP(S) URLs.**
  - **Why:** Quick Lookup opens saved evidence directly, including suppressed and source-less records, without searching or paging through the Atlas list.
  - **What:**
    - Browser and API clients resolve canonical values in personal, team, or explicit Project scope and reuse the same bounded Overview, Evidence, Findings, and Intel profile shown in Atlas.
    - Invalid input, no-record results, bounded legacy ambiguity, and unmatched URL parent hosts stay distinct and recoverable. **Open in Atlas** is an explicit transition, while search, scope switching, copy, and command-prefill actions remain non-destructive.
    - Lookup reads only saved evidence and owner-scoped Intel snapshots. It doesn't create records, run commands, contact providers, or log submitted and canonical values; **Refresh intel** remains a separate action.
    - Owner changes clear stale results, irrelevant Atlas list and bulk loads stay out of lookup mode, and the type/signature index keeps exact candidate searches efficient on SQLite and Postgres.
  - **Tests:** Resolver, route, API, browser, PostgreSQL, privacy, logging, query-plan, and bundled/source Playwright coverage is summarized in the Tests section below.
- **Quick Lookup is available beside Atlas throughout the shell.** The desktop rail, mobile application menu, and `Alt+Q` / `Option+Q` shortcut all open the same lazy Atlas lookup mode without adding another modal or increasing the initial shell payload. Using the active entry again closes Quick Lookup instead of resetting the current result in place.

### Changed

- **Atlas lookup and CVE-risk queries now make their trusted SQL fragments explicit.** Named templates keep generated placeholders and validated scope, owner, and ordering clauses separate from bound values, removing stale Bandit suppressions without changing query behavior.
- **Fresh Postgres databases load the bundled CVE-risk baseline through a bulk staging merge.** The offline EPSS and CISA KEV baseline remains part of guarded startup maintenance, while clean installations avoid hundreds of thousands of individual upserts before the app becomes ready.
- **JavaScript development dependencies now include current security fixes for brace expansion, URL parsing, and HTTP handling.** The locked dependency tree uses `brace-expansion` 5.0.9, `fast-uri` 3.1.5, and `undici` 7.29.0, clearing the reported high-severity advisories without changing the app's runtime behavior.
- **The cryptography runtime dependency now uses 50.0.0.** This includes the upstream fix for CVE-2026-69247 while keeping the app's existing certificate parsing and encrypted-secrets behavior.
- **Atlas entity details now put app-captured evidence before external provider data.** Domain and IP profiles separate findings on the host from findings on their immediate URL and port children, show a clearly labeled combined host-surface total, and list both related URLs and related ports with working pagination. A new scan-coverage section distinguishes app-captured ports, scans that surfaced no ports, and entities without an app port scan. Host profiles also show a bounded app-captured port list with protocol, service, version, banner availability, sightings, last-seen time, and source-run count. URL profiles can reuse that list only as clearly labeled parent-host evidence. Project Overview and Atlas now calculate direct finding totals, severities, review states, verification states, suppression, occurrences, and latest activity through the same contract; suppressed findings stay visible as a separate count without inflating active review or verification work. Cached Intel also uses one coverage and freshness contract across both surfaces, including provider and snapshot counts, last refresh time, high-signal highlights, certificate state, and a provenance-aware comparison of app-captured and provider-reported ports. Domain profiles surface relevant certificate evidence, while host profiles label recorded port differences without turning them into findings; raw provider responses remain in the existing expandable collection. Project-filtered profiles add the selected entity's watcher state and recent matched changes, while owner-wide profiles omit Project monitoring instead of presenting project activity out of context. The quick detail pane follows a stable Observed, Findings, Relationships, Evidence, Metadata, then External intelligence order, gives section separators balanced breathing room, and caps long finding, relationship, port, run, and import collections at three rows before linking to the focused profile. Direct findings and related entities use the same full-width clickable row treatment as the rest of Atlas, while a source run's command opens Run Details and its cleanup action stays in the focused Evidence view. Direct findings return to the same profile scroll position, linked projects can be opened without removing their link, and URL or port details link back to their stored parent host. The same owner or project scope is carried through the browser route and API v1 response, whose compatible detail payload now also groups the normalized overview as observed evidence, finding summary, relationships, and Intel.
- **Atlas now offers focused entity profiles without leaving the current results.** **View profile** expands the existing dialog into Overview, Evidence, Findings, and Intel views, while **Back to results** restores the active filters, page, selected row, and reading position without reloading unrelated detail. On both desktop and mobile, the existing profile now shows the canonical identity, first and last observation, project-link count, suppression, and missing-source state above its tabs and includes a **Copy value** action. Finding summary cards open exact direct, related-URL, related-port, or combined result sets instead of widening the query behind the displayed count. Related entity profiles can return to the previous entity and local view, Project round trips reopen the same Atlas profile, and finding review changes refresh the affected detail without reloading the result list. Provider/app port differences link directly to the app evidence and cached provider data that explain them. Empty and partial profiles point to the next useful action, including running a scan, refreshing Intel, or opening the parent host. Entity links from transcripts, Run Details, Projects, and Project Overview open the focused profile immediately. Mobile uses the same views and its existing drill-in navigation instead of stacking another overlay.

## [2.8.3] - 2026-07-29

### Fixed

- **GELF status fields now keep one OpenSearch-compatible type across the event stream.**
  - **Root cause:** request logs used the generic `_status` field for numeric HTTP codes while Intel provider and other lifecycle events reused it for text such as `ok` and `error`. Once OpenSearch mapped `_status` as a number, it rejected later text values with `mapper_parsing_exception`.
  - **Fix:** HTTP codes now use numeric `http_status`, while provider, workflow, schedule/watcher, AI, Project, team, and export states use feature-specific string fields. The shared GELF boundary no longer emits `_status`; it safely routes any remaining generic or invalid status value away from established numeric mappings.
  - **Tests:** formatter coverage exercises current semantic status fields, legacy numeric and string status payloads, invalid HTTP values, and explicit-field precedence. Existing request, Intel, AI, team, Atlas, Project, and export-log assertions now pin their replacement fields without increasing the test count.

## [2.8.2] - 2026-07-28

### Fixed

- **Production lifecycle commands now keep operator Compose overrides active.** When `compose.operator.yaml` exists beside the installed stack, `darklab-deploy` includes it for backup, restore, database migration, upgrade validation and printed restart commands, and removal. Restored containers no longer restart from the release-owned base alone.

- **History bulk deletion now follows the active filters and previews the exact number of affected runs.** The confirmation shows matching and non-favorite totals, and both desktop History and mobile recents delete the complete filtered result set instead of clearing unrelated runs or processing only the first page.

- **Unassigned watcher Project scope is now represented consistently in run-finalization type hints.** This removes a false editor error from the watcher-scope regression coverage without changing runtime behavior.

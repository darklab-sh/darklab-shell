## [2.8.4] - Unreleased

### Added

- **Assessment batches now share a complete child-run launch boundary with durable workflows.**
  - **Why:** A mixed assessment plan needs to launch independently rendered commands without weakening the workflow engine's run binding, privacy, or recovery guarantees.
  - **What:** Workflow template and collection rendering now lives in a workflow-only adapter that produces a surface-neutral child launch specification. The shared downstream launcher accepts the execution command, public display command, private values, and trusted run context directly, while existing workflow fan-out keeps its current output, limits, Project linking, and failure behavior. Durable coordinator rows also carry an explicit execution kind; workflow routes, quotas, recovery, metrics, and History provenance accept only workflow rows, leaving assessment batches a separate product surface even though both can reuse the same lifecycle tables. The batch storage contract adds one durable parent, ordered immutable events, lossless chunks of at most 32 items, a mandatory 512-item ceiling, fixed one-at-a-time target work, and bounded batch, owner, and instance concurrency. Dedicated preview and item records hold bounded public plans and separate frozen-check mappings without putting heterogeneous commands into workflow child rows. Shared plan-policy helpers keep finding retests check-specific while giving assessment batches a separate execution key that can deduplicate identical commands across frozen checks without treating their coverage identities as one.
  - **Tests:** Existing durable workflow integration coverage now pins the adapter's public/private command split, empty trusted-argument behavior, and execution-kind isolation. Migration and architecture contracts cover the discriminator, backend-neutral batch parent, preview, item, mapping, and event schemas, kind-aware indexes, fixed limits, exact chunk partitions, deterministic progress rollups, and focused module budgets while keeping the existing fan-out launcher baselines unchanged. Storage coverage also proves atomic 32/33-item initialization, owner-scoped active limits, monotonically ordered sanitized events, cursor paging, preview and execution mapping cascades, and parent cleanup. Policy coverage proves check-independent execution identity, unchanged check-specific retest grouping, exact bounds and command matching, safe-policy selection, and credential exclusion.
  - **Preview storage:** Server-owned previews validate credential-free probe plans, hash the complete snapshot, expire after 15 minutes, and page complete items within count and byte limits without creating coordinator or run rows.
  - **Preview compiler:** One bounded cycle read now separates safe defaults from unchecked standard actions, applies explicit target and category selections, explains manual, evidence, policy, scope, feature, connector, takeover, and saved-artifact exclusions, and flags discovered or infrastructure targets for review without changing the assessor's selection. It reuses one current probe-readiness snapshot, deduplicates only exact public plans, preserves every frozen-check mapping, rejects every item, mapping, row, and memory overflow instead of truncating, and estimates ordered 32-item chunks with both batch and per-target concurrency.
  - **Scope qualification:** Discovered targets name the source that introduced them and ask the assessor to confirm whether they are intended or third-party infrastructure. Personal and Team role coverage proves viewers can preview while only operators, admins, and owners can start or cancel work, and direct exclusion tests pin intrusive, destructive, takeover-confirmation, OAST, Schemathesis, and non-runnable ZAP-shaped actions outside every batch.
  - **Preview API:** Browser viewers and API tokens can create the same 15-minute server-owned preview, reread its compact approval summary, and page complete items through owner-scoped routes. Requests stop at 64 KiB, pages stop at 100 items or 1 MiB, invalid cursors and stale snapshots return stable errors, and previewing still creates no coordinator, run, or audit event.
  - **Preview tests:** Focused coverage proves deterministic full-snapshot digests, atomic writes, owner isolation, expiry, 100-item paging, the 1 MiB response boundary, safe-default and explicit-standard selection, cross-check execution deduplication, manual and evidence exclusions, changed target confirmation, read-only compilation, and the 32/33-item chunk boundary.
  - **Confirmed start:** The server now rebuilds the saved selection against current cycle state, checks the complete approval digest, and requires a second confirmation for standard work before atomically claiming the preview and copying every selected plan and check mapping into one immutable coordinator. Matching retries return the same batch without starting duplicate work, including after preview expiry or later cycle changes.
  - **Confirmed-start tests:** SQLite and PostgreSQL coverage pins exact preview-to-execution parity, separate confirmations, scope-drift rejection, rollback on copy mismatch, zero run creation during start, owner active limits, and idempotent replay.
  - **Fair claims:** Assessment batches now claim heterogeneous items through the shared workflow checkpoint transition while enforcing their saved per-batch limit, one active item per target, and the most restrictive owner and instance limits in one serialized transaction. A busy target can defer without blocking unrelated targets later in the stable item order, and a claim records its parent, chunk, and item progress without creating a run.
  - **Claim tests:** SQLite coverage pins stable target-aware selection, authoritative child and checkpoint state, sanitized ordered events, zero run creation, and batch, owner, target, and instance deferrals. PostgreSQL route coverage crosses the same advisory-lock and claim query path, while the existing workflow suite protects optional empty fan-out and recovery behavior after the shared claim extraction.
  - **Item execution:** Each claimed item rebuilds its exact probe plan against current Project scope, target confirmation, policy, feature readiness, and profile identity before the shared child launcher receives it. A changed or unavailable plan settles with a stable reason and no run; an approved plan keeps its reviewed display command, binds the ordinary run directly to the Project, retains private launch material outside durable batch rows, and suppresses per-child completion notifications. Run finalization advances the authoritative checkpoint and sanitized event stream once, refills available slots, crosses 32-item chunk boundaries without truncation, and leaves an already-saved run intact if coordinator advancement fails.
  - **Execution tests:** Focused SQLite coverage pins exact revalidation, stale-plan settlement, Project-linked run binding, public-command equality, private launch separation, child-notification suppression, sanitized item events, terminal and cross-chunk completion, and isolation from durable workflow finalization. Existing workflow tests continue to cover the shared launcher, retry policy, failure cleanup, and ordinary run notifications.
  - **Truthful cancellation:** Canceling a queued or running batch now stops new claims in the same serialized claim gate, cancels work that never launched, and signals each bound ordinary run through the existing scoped process-group boundary. The parent remains `canceling` while any child is still active, preserves work that already succeeded, and reaches `canceled` only after every child settles. A failed signal remains visible as `could_not_cancel` instead of claiming that the process stopped, and cancellation never creates a retry attempt.
  - **Cancellation tests:** Focused coverage pins immediate queued cancellation, idempotent requests, active-run signaling, delayed parent settlement, no-retry finalization, truthful failed-signal rollups, sanitized events, scoped process-group use, and unchanged module-size and security gates.
  - **Lifecycle conflicts:** Completing, archiving, or deleting an assessment—or deleting its Project—now cancels every matching active batch before changing lifecycle state. The first request returns a stable cancellation-pending conflict with the affected batch ids and never saves the requested change; after all children settle, the operator must make a fresh request. Project deletion then removes terminal batch coordinators and previews while retaining the ordinary child runs and evidence that Project cleanup already preserves.
  - **Lifecycle tests:** Browser and API coverage pins the shared conflict payload, unchanged assessment and Project state, multiple-batch cancellation, fresh-request requirement, and terminal coordinator cleanup.
  - **Startup recovery:** Web startup now recovers assessment batches through a kind-specific bounded cursor after ordinary workflow recovery. It releases abandoned unbound claims, replays saved completions, leaves live child runs attached, classifies missing broker state through the existing retry limit, and resumes eligible work without launching the same item twice. A missing or archived Project, inactive assessment, expired coordinator, lost permission, or malformed snapshot stops new claims and leaves bound processes in `canceling` until their real outcomes settle; the parent then reports the durable failure reason instead of a false cancellation.
  - **Operator limits and cleanup:** The validated `assessment_batches` YAML section can lower the 128-item selection limit, active-parent quota, batch/owner/instance concurrency, four-hour runtime, and 30-day terminal coordinator retention without raising the fixed product caps or changing one-at-a-time work per target. Startup cleanup runs after recovery, removes only old terminal retry-chain leaves, preserves the source of every retained retry, and never deletes ordinary child runs or their evidence.
  - **Recovery tests:** SQLite and PostgreSQL coverage pins abandoned-claim events, completion replay, live-run attachment, bounded missing-run retries, canceling recovery, scope, runtime, and permission loss, malformed checkpoint handling, kind-isolated paging, per-row error isolation, bounded recovery metrics, and startup ordering after workflow recovery. List and item responses are bounded to 100 records, item pages also stop at 1 MiB, foreign-owner identifiers stay indistinguishable from missing ones, and skipped work remains distinct from canceled work in every rollup.
  - **Read-route tests:** Focused SQLite coverage pins Project and assessment filtering, list, item, and event cursors, response boundaries, latest-attempt selection, stable skipped counts, browser/API parity, invalid cursors, and owner isolation. The checked-in OpenAPI contract includes the same durable batch, item, event, progress, and pagination shapes.
  - **Child-run provenance:** Every ordinary run launched by an Assessment batch now carries a bounded public link back to its batch, cycle, and item. History, Run Details, Project runs, Recent evidence, API run summaries, comparisons, reports, and evidence packages show that source and can return the assessor to the exact batch. Coordinator rows still omit commands, targets, profiles, output, and private launch material; evidence reconciliation continues to use the ordinary run and each frozen check mapping independently.
  - **Provenance tests:** SQLite and PostgreSQL coverage follows one child through browser and API History, Project and Assessment reads, report and package rendering, exact batch navigation, mapped-only evidence reconciliation, and owner isolation. Contract tests pin the nullable OpenAPI fields, prove that compatible but unmapped checks remain untouched, and show that public ancestry never exposes batch plan or output data.
  - **Start and cancel API:** Authorized browser and API clients can submit the reviewed preview id, complete digest, and explicit confirmations to start a batch through one shared lifecycle service. Repeating the same confirmation returns the original coordinator, ordinary runs start only in currently fair slots, and Project-scoped cancellation stops new claims before signaling active runs. Both mutations have fixed 16 KiB request limits, `RUN_COMMANDS` capability checks, bounded audit details and metrics, stable error envelopes, and no target values or commands in log labels.
  - **Mutation-route tests:** Focused browser and API coverage pins idempotent start, one durable coordinator, Project-scoped cancellation, viewer rejection, unsupported and oversized request bodies, audit events, OpenAPI shapes, and truthful handling when the process-cancellation boundary returns either an error or an explicit rejection.
  - **Browser assessment plans:** The Assessment tab now lets viewers build a read-only plan for an active cycle and lets operators start it after reviewing the selected targets, categories, exact commands, policy, bounds, skipped reasons, potential coverage, and estimated completion window. Safe work is selected by default; standard work stays separate until it is explicitly included and confirmed, and that confirmation repeats the target and command counts, fan-out and concurrency, request and time bounds, and credential classification. The durable **Assessment batch** monitor restores after reload, refreshes every command page the assessor has opened, shows item and event progress, opens child runs in History, and requests cancellation without erasing completed runs or evidence. Queued and active states use the shared caution color, successful work uses success, failed or could-not-cancel work uses error, and neutral terminal outcomes stay muted.
  - **Browser tests:** Focused Vitest coverage pins safe and standard selection, viewer permissions, stale-preview invalidation, confirmation, reload recovery, History handoff, partial-outcome colors, private-field non-rendering, cancellation, and multi-page polling. Source and bundle Playwright coverage crosses the assembled Assessment surface from a real server-owned preview through start, reload recovery, and cancellation.
  - **Headless batch control:** `darklab assessment batch plan`, `start`, `list`, `show`, `follow`, and `cancel` expose the same server-owned preview, digest confirmation, durable progress, item pages, sanitized event cursor, and truthful cancellation contract to scripts and local shells. Plan and start accept explicit target and category includes or exclusions plus bounded concurrency; safe work remains the default, standard work needs its own acknowledgement, and start or cancel stays read-only without `--confirm`. Following a terminal batch returns distinct exit codes for complete success, partial results, cancellation, and failure, while Ctrl+C prints the exact cursor needed to resume without canceling work.

Architecture budgets keep each new parser, paging, formatting, preview, and lifecycle module independently ratcheted.
  - **Immutable retries:** A terminal Assessment batch can now build a fresh current-state preview for its failed, unavailable, interrupted, skipped, or canceled work.
